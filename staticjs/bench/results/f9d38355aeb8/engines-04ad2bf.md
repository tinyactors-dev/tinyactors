## Method

- **The cases** are bench/bench.c's own (listed in bench/engines/cases.mjs, with the size each runs at): the same source, the same globals, the same fixtures. bench/engines/dump.c reads them from bench.c; the JavaScript engines build the fixtures with bench/engines/guest.js, which mirrors bench.c's generators.
- **Verified before timing.** For every case, at its smoke size and at the measured size, each fixture as staticjs's writer writes it (from bench.c's own generators) has the same length and FNV-1a hash as guest.js's in each engine; each engine's result has the same length and hash as staticjs's; and at the smoke size each engine's result prints as bench.c's expected value. A difference stops the run, naming the case (the Verification section lists what was checked).
- **staticjs** is build/release/bench (`mise run bench`'s build), run as `bench --only=CASE --size=N`: per op, sjs_vm_start, run, take the result, release it, with the program compiled once and the globals bound once; the figure of a run is the median of its samples.
- **Node JIT and Node --jitless** run a guest program (bench/engines/guest.mjs: guest.js, the fixtures, and the case's source as an arrow function) evaluated once in the runner's realm. One sample is one call `__bench.run(k)`, which calls the case k times inside the engine and adds up a fold of each result (its length, size or value), so that no engine can drop the work. The host clock is read around that call.
- **quickjs-wasi** runs the same guest program in QuickJS-NG compiled to WebAssembly (the npm package, pinned in bench/engines/package-lock.json), in a fresh instance per process; one sample is one `evalCode("__bench.run(k)")`, so the crossing between the host and the guest is paid once per sample, not per op.
- **Calibration.** In every engine k grows (×8 while a sample takes under a tenth of the target, then ×2) until one sample takes at least 30 ms; then the warm-up, then 3 samples, whose median is the run's figure.
- **Interleaved rounds.** Each case runs 5 rounds; a round runs the four engines one after another, each in a process of its own, never two at once: staticjs, Node, Node --jitless, quickjs-wasi, and the next round in the reverse order, so that a drift of the machine does not favour one engine. A cell is the median of the rounds' figures.
- **Spread and ≈.** Each engine's range is that of its middle rounds (the fastest and the slowest dropped, with four rounds or more; all of them otherwise). A cell shows ±half that range, as a percentage of the median, when the range exceeds 10%. A ratio is marked ≈ when staticjs's range and the other engine's overlap: that ratio is not resolved, and the two may be equal.
- **Ratios** are the other engine's time divided by staticjs's: "2.0× faster" means staticjs takes half the time of that engine, "2.0× slower" twice the time.

- **staticjs** counts every byte through the bench's allocator, in one untimed op: setupBytes is everything live after setup (the context, the compiled program and the inputs, so about 100 KiB at n = 1), peak is the op's transient high-water mark above that, held is what its result keeps while held.
- **quickjs-wasi** is QuickJS's own malloc accounting (`getMemoryUsage().mallocSize`) after a full collection: fixtures is what the guest program holds at n beyond what it holds at n = 1, held what one result adds while held. It has no peak.
- **Node** is heapUsed + external after two full collections (--expose-gc), around holding one result: the runner's own objects share that heap and collections are not exact, so it is only indicative and can be negative.
- The three represent values differently (staticjs's values, QuickJS's JSValues and shapes, V8's tagged pointers and hidden classes), so equal work need not take equal bytes.

## Caveats

- **Compile rows are lazy in V8.** `new Function(source)` makes V8 pre-parse the inner functions and compile only the outer one; a function is compiled when first called. staticjs and QuickJS compile every function to their bytecode at once. The compile rows therefore favour Node.
- **Modules are emulated.** The guest is a script, so power.js and campaign.js run as function bodies (exports become consts, the import is dropped). eval.module.power runs that body each op in the JavaScript engines; staticjs evaluates its compiled module program.
- **One call per op in staticjs, one loop in the guest elsewhere.** staticjs's op is a whole embedder evaluation (start, run, take the result, release); the other engines' op is a call of a function inside a warm loop, which a JIT can inline and specialise. The start-up table gives what one evaluation from the host costs in each.
- **Noise.** Figures move by several percent between processes and by more between days; compare runs from one machine signature and one day only, and read nothing into a ratio marked ≈.
- **Not a conformance claim.** The cases are the subset staticjs supports; the other engines run full JavaScript.
