# The choices an application makes

Each choice below says when to pick which, and what it costs. The
packages' guides have the details (`docs/guide/<name>.md` in
`@tinyactors/node`; the Python README's sections of the same names).

## The datamodel: native or quickjs (Node.js, Bun)

| | `datamodel: 'native'` (the default) | `datamodel: 'quickjs'` |
|---|---|---|
| Runs chart code in | your own engine (`node:vm` contexts) | QuickJS, a separate engine in the package, with no I/O |
| Pick it for | charts you wrote: trusted code | charts you did not write: uploaded by users, generated by a program |
| Limits | none: a `vm` context is not a security boundary | `quickjs: { maxOps, memoryLimit }`; a busy loop or a hoard ends in `error.execution` |
| Hibernation stores | values of the value table only (a `Map` or `Date` in a variable keeps the actor in memory) | QuickJS's own values too (`Date`, `Map`, `Set`, cycles) |
| Scripts | a chart-level `function` is a helper of the chart; a top-level `var` a variable of the session; top-level `let`, `const`, `class` refused | a chart-level script runs as global code of the actor's context |

A host uses one datamodel for all its charts. Write charts that run on
both (helpers that take what they read as arguments, no top-level `let`)
and test on both ([testing.md](testing.md)). With Python,
`datamodel="python"` charts are trusted code; `ecmascript` charts run on
quickjs.

## What survives a restart

A host keeps nothing on disk by itself. Pick per kind of actor:

| Way | What it keeps | Cost | Pick it when |
|---|---|---|---|
| **store + `resident`** (hibernation) | idle actors as blobs in your store, so memory holds only the busy ones | blobs wake only in the host that wrote them, or one restored from its later snapshot: not durability on its own | many long-lived actors, mostly idle |
| **snapshots** (`host.snapshot()`, `Host.restore`) | the whole host at one moment: actors, timers, queues, the images | a snapshot of a quiescent host only; what happened after the last snapshot is lost unless your database has it | restarts and deploys of one process; rehearsing a deploy on a copy |
| **your database as the truth** | rows you write through an I/O processor; actors rebuilt from them at start | you write the rebuild (spawn params from the row, a first state that routes on a phase) | data other programs read, audit, or loss you cannot accept |

They combine: snapshots plus the store for the actors' state, and a
ledger of every change in your database for audit and recovery. Keep the
store's file with the snapshot: a restored host wakes the blobs of the
host it was taken from.

```js
import { compileCharts, Host, MemoryStore } from '@tinyactors/node';

const compiled = compileCharts([{ name: 'account.scxml', text: `
<scxml xmlns="http://www.w3.org/2005/07/scxml" version="1.0"
       datamodel="ecmascript" name="account" initial="active">
  <datamodel><data id="balance" expr="0"/></datamodel>
  <state id="active">
    <transition event="deposit"><assign location="balance" expr="balance + _event.data.amount"/></transition>
    <transition event="balance"><send targetexpr="_event.origin" event="current"><param name="balance" expr="balance"/></send></transition>
  </state>
</scxml>` }]);
const store = new MemoryStore();            // SQLiteStore('accounts.db') keeps them in a file
const host = new Host(compiled, { system: 'bank', store, resident: 1 });
compiled.close();

const accounts = ['a.1', 'a.2', 'a.3'].map((name) => host.spawn('account', { name }));
for (const account of accounts) account.send('deposit', { amount: 10 });
await host.idle();
console.log('blobs in the store:', store.blobs.size);
host.actor('a.1').send('deposit', { amount: 5 });   // wakes a.1 from its blob
console.log(await host.actor('a.1').ask('balance'));
host.close();
```

```output
blobs in the store: 2
[ 'current', { balance: 15 } ]
```

An actor hibernates only at rest: no events waiting, no invoked
services or child charts running, and every variable a value its
datamodel can write out.

## An I/O processor or an invoked service

| | I/O processor (`<send type>`) | Service (`<invoke type>`) |
|---|---|---|
| Lifetime | one send, one optional answer | while the invoking state is active; cancelled when it is left |
| Shape | an object with `receive(send)` | a handler `(invocation) => service`, the service with optional `receive(send)` and `stop()` |
| Talks back | `send.answer`, `send.fail` | `invocation.sendBack(event, data)`, `invocation.done(data)` (`send_back`, `done` in Python) |
| Pick it for | a request and its reply: a database write, an HTTP call, a mail | something that runs: a connection, a subscription, a subprocess, a long computation |
| Blocks hibernation | no | yes, while it runs |

A service's failure (no handler for its type, a handler that throws) is
`error.communication` for the invoker. A restored host announces each
service that was running, so your handler starts it again.

## Spawner and collection actors

`<invoke>` of a chart starts a child that stops when the state is left.
For actors that outlive their creator's state, give the host
`ioProcessors: { spawn: new Spawner() }` (`tinyactors.Spawner()`): a
chart sends `{chart, name, params}` and gets `spawned` with `{name,
address}`, or `error.communication`. The actor that sends those is a
collection actor, the one owner of those names
([designing-actors.md](designing-actors.md)).

## ask, or a send and a transition

`await actor.ask(event, data)` is for your program asking an actor and
waiting for its answer (a status page, an admin command, a test). Between
actors, send and handle the answer in a transition, with a timeout: a
chart never blocks.

## Other systems

A send to another system's address (`tinyactors://billing/...`) goes to
your host's `transport` handler. Your transport carries `send.message`
(over a socket, a queue, HTTP) and the other side gives it to its
`host.send(message)`; a failure it learns of is `host.fail(target,
sendid)`. Encoding, delivery and trust are yours. Use it for actors in
another process, another machine or a browser; inside one process, one
host with several segments is simpler. Guide: `other-systems.md`.

## Telemetry

Give the host's config a `telemetry` section and the `telemetry` handler
an exporter: the core encodes traces and logs as OTLP for your collector,
and `host.metrics()` gives the counters. A W3C `traceparent` passed to
`spawn` or `send` continues your request's trace through the actors.
Guide: `telemetry.md`.

## A new version of a chart

Adding an image with a chart of the same name is a deploy: new actors run
the new version, running ones finish on theirs. To move running actors,
`host.migrate({ chart })`: each moves at its stable point, keeps its
session, states (matched by id), timers and services, and first gets
`error.platform.upgrade` with its old variables. Rehearse a migration on
a restored snapshot. Guides: `migration.md`, `snapshots.md`.
