# Developing tinyparse

The contributor's guide: building from source, the test suite, the correctness
gates a change must clear, and how to run the benchmarks. For *using* the library
see [README.md](README.md); for the design see
[tinyparse-design.md](tinyparse-design.md).

## Building from source

tinyparse is plain C11, one project of the tinyactors monorepo, built by
Ruby file tasks in [mise/tasks/](mise/tasks/) with the toolchain the root
`mise.toml` pins (see the monorepo's `docs/build/`): the pinned clang 22 for
what runs on this machine (`Toolchain::Target.host`), zig cc for what is
shipped (`Toolchain::Target.release`). Nothing is taken from `PATH`.

```sh
mise install          # at the monorepo root: clang, llvm-tools, zig, ruby, ast-grep
mise run build        # build/: libtinyparse.a, the CLI, the harness, the examples
mise run dist         # dist/<target>/: libraries and CLI for x86_64-linux, aarch64-macos
mise run amalgamate   # dist/amalgamation/: the single-file distribution
mise run release      # dist/release/: the release tarballs
mise run test         # the suite over the xfail ledger, and every gate
mise run test --full  # the same, with each gate's exhaustive version
mise run gate:cc-diff # one gate (--full for its exhaustive version)
mise run clean        # remove build/ and dist/
```

Every task compiles and links by content (the monorepo's `mise/lib/cache.rb`),
so a second run costs a few hashes. The generated headers the CLI embeds (the
manual page, the standard grammars, the library amalgamation) are written to
`build/generated/` by `mise run generate`.

## The test suite

Progress is a data-driven, ratcheting suite under [test/](test/), interpreted by
`test/harness.c` against `test/xfail.list`: done means every case passes and the
xfail ledger is empty. The plan is in [docs/build-plan.md](docs/build-plan.md).
Each example under [examples/](examples/) is pinned by a case under `test/suite/`
so its lesson — including the nested one, where the lesson is recursion — stays
green.

## Correctness gates

tinyparse runs more than one engine over a grammar, and they must agree byte
for byte. Each gate is a Ruby file task in [mise/tasks/gate/](mise/tasks/gate/)
(sharing [mise/lib/gate.rb](mise/lib/gate.rb)), and `mise run test` depends on
every one, so they run side by side before the suite. A gate takes a second or
two; one with an exhaustive version (a sweep of every corpus input, a larger
workload) declares `--full`, which `mise run test --full` and the root's
`mise run test:full` run. Each works in its own temporary directory.

- **cc-diff** — parsers generated by `tinyparse c --parser` against the VM, on
  the json family, std.fence, the heredoc grammars and the corpora (`--full`:
  every JavaScript, TypeScript and shell input).
- **vm-diff** — the VM with its rule memo adaptive and forced on against the
  memo off, on the same inputs, every example grammar and
  `test/gates/backtrack.scm` (`--full`: every corpus input). That grammar is the
  one that makes the memo replay a cached success and wakes the adaptive memo
  mid-parse, and the gate checks both happened (the trace events `rule.replay`
  and `rule.memo-on`); no corpus reaches either. It also checks that the library
  calls no actor runtime.
- **diag-diff** — the generated parser's diagnostics against the VM's on a
  broken-input corpus, so error reporting may be extended but never regressed.
- **import-c**, **multiparser**, **nesting**, **bufferfriendly** — a grammar that
  imports another, two prefixed parsers in one program, generated parsers nested
  through the language registry, and a generated parser fed a growing buffer
  (lists, and top-level atoms a chunk boundary splits): each builds the VM's
  tree and the committed golden. The nesting driver also reports how many
  regions each registered parser parsed, since the inject runtime's fallback
  to the VM builds the same tree.
- **exports** — a shared object built with `examples/embed/embed-lib.sh` exports
  its parsers' entries and the public API, nothing else (`--full`: at -O2).
- **vm-nocrash**, **parser-nocrash** — the VM and the generated std.json and
  std.shell parsers survive a deeply nested input under a 512 KiB C stack
  (`--full`: also the JavaScript and TSX parsers, whose frames are largest).
- **reclaim**, **reuse-regression** — one engine across many parses stays at
  about one parse's memory and builds the same tree every time (`--full`: 300
  parses; std.tsx).
- **no-statics** — no mutable static storage in the library: the ast-grep rule
  `tinyparse-no-static-mutable` (in the monorepo's `mise/ast-grep/rules/`) over
  `src/*.c`, and no writable data symbol in `libtinyparse.a` or in the parsers
  `tinyparse c --parser-lib` generates for std.json, std.fence and std.shell.

A change that alters the tree updates the goldens deliberately; a change that
claims to be performance-only keeps every gate green unchanged. The project
records the measured floor rather than tuning to a marker: where a generated
parser does not yet beat its target, [docs/peg-vs-glr.md](docs/peg-vs-glr.md) and
[docs/decisions.md](docs/decisions.md) say so and leave the win unrecorded until
it is earned.

## Benchmarks

Benchmarks and corpus counts are opt-in tasks in
[mise/tasks/bench/](mise/tasks/bench/), never part of `mise run test`: they
measure time, so they run alone, and most need the network. They are bash
scripts in [bench/](bench/), reproducible per the methodology in
[docs/performance.md](docs/performance.md):

```sh
mise run bench:fetch                # the references of reference/PINS.txt, by tarball
mise run bench:javascript           # JavaScript corpus: VM vs tree-sitter
REGEN=1 mise run bench:react        # React: parse + collect; builds the manifest
mise run bench:parsers              # React: six parsers, parse-only
mise run bench:tsc                  # React: tsc and tsgo, parse-only
mise run bench:javascript-coverage  # JS_COVERAGE=parsed/total over tree-sitter's corpus
mise run bench:typescript-coverage  # TS_COVERAGE=parsed/total
mise run bench:perf-gate            # the suite, then bench:javascript under test/perf-baseline.txt
mise run bench:rule-memo            # the CLI's time with the rule memo off and on
```

The pinned references live under [reference/](reference/) (see
[reference/PINS.txt](reference/PINS.txt)); they are gitignored, and
`mise run bench:fetch` downloads each as a tarball at its pinned commit.

## Running the benchmarks under Claude Code on the web

The remote/web execution environment adds friction a normal workstation does not.
These are the blockers and the workarounds, recorded so the next session does not
rediscover them.

- **The git proxy may be scoped to the session's repository.** Where an outbound
  `git clone` of another GitHub repository is refused, fetch the references as
  tarballs through the egress HTTPS proxy, which `mise run bench:fetch` does
  (`codeload.github.com` is reachable). In the session that moved tinyparse into
  the monorepo, `bench:fetch` and the scripts' `git clone` of the tree-sitter
  runtime both worked.

- **A tarball runtime is not a git checkout.** The bench scripts record the
  tree-sitter pin with `git -C "$runtime" rev-parse HEAD`; over an extracted
  tarball that command walks up to the enclosing repository and prints the
  wrong commit. Trust the commit you fetched.

- **`tsgo` may not build here.** The sixth arm of `bench:parsers` needs a
  `typescript-go` clone plus a full Go build that pulls a large module graph;
  where that fails it is reported as not obtained rather than staged. `tsc` and `meriyah` install fine from npm.

- **`TINYPARSE_RULEMEMO=always` over React does not finish.** Forcing the rule
  memo on from the first call is impractically slow at the default iteration
  count; the published numbers use the adaptive default, which stays dormant until
  a parse goes super-linear.

- **`bench:parsers` needs the React manifest first.** Run
  `REGEN=1 mise run bench:react` before it, or it aborts on a missing
  `bench/react-corpus/MANIFEST.txt`.

- **Profile the built harness directly.** The old `bench/prof/` driver is gone,
  but `bench/bench_tinyparse` carries function symbols, so run it straight under
  callgrind (see the performance doc's appendix).
