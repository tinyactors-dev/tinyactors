# The quickjs sandbox

A host runs its charts' JavaScript on one of two datamodels. They take
the same charts, and a host uses one of them for all its charts:

- **`native`** (the default) runs chart code in `node:vm` contexts of
  your own engine, V8 under Node.js and JavaScriptCore under Bun. It is
  fast and its values are your engine's, but a `vm` context is not a
  security boundary: a chart can reach the process it runs in.
- **`quickjs`** runs chart code in QuickJS, a separate JavaScript engine
  compiled into the package, with no I/O at all (no modules, no timers,
  no files, no network) and limits on how long an evaluation runs and how
  much memory the engine takes.

Choose quickjs for charts you did not write or do not trust: charts your
users upload, charts from another team's service, charts generated by a
program. Chart code on the native datamodel is trusted code.

```js
import { compileCharts, Host } from '@tinyactors/node';

const compiled = compileCharts([{ name: 'uploaded.scxml', text: `
<scxml xmlns="http://www.w3.org/2005/07/scxml" version="1.0"
       datamodel="ecmascript" name="uploaded" initial="s">
  <state id="s">
    <transition event="spin"><script>while (true) {}</script></transition>
    <transition event="hog"><script>const hoard = []; for (;;) hoard.push(new Array(1000).fill(1));</script></transition>
    <transition event="peek"><log expr="typeof process + ' ' + typeof require + ' ' + typeof setTimeout"/></transition>
    <transition event="error.execution"><log expr="'stopped: error.execution'"/></transition>
  </state>
</scxml>` }]);

const host = new Host({ systemID: 'sandbox' }, {
  datamodel: 'quickjs',
  quickjs: { maxOps: 1000, memoryLimit: 16 * 1024 * 1024 },
  log: (host, entry) => console.log(entry.text),
});
host.addImage(compiled.image);
compiled.close();

const actor = host.spawn(host.chart('uploaded'));
host.send(actor, 'spin');
host.send(actor, 'hog');
host.send(actor, 'peek');
await host.idle();
host.close();
```

```output
stopped: error.execution
stopped: error.execution
undefined undefined undefined
```

An evaluation that runs too long or asks for too much memory is stopped,
and the actor gets `error.execution`, as for any expression that throws;
it goes on with its next event.

## The limits

`options.quickjs`, with `datamodel: 'quickjs'` only (with the native
datamodel it is a `TypeError`):

| Option | Default | What it bounds |
|---|---|---|
| `maxOps` | 1,000,000 | the engine's interrupt checks one evaluation may make before it is stopped |
| `memoryLimit` | none | bytes for the whole engine, every actor of the host together |
| `stackLimit` | the engine's | bytes of native stack for JavaScript |
| `realm` | `'auto'` | `'isolated'` gives every actor a context of its own (below) |

Set both `maxOps` and `memoryLimit` for untrusted charts. `maxOps` is
not time: it counts the engine's interrupt checks, one for every 10,000
jumps and calls QuickJS counts down, and how long a check takes depends
on the code between them. The time a looping evaluation holds
the host (and every host of the thread, since they share it), measured
on x86_64 Linux, Intel Xeon @ 2.10GHz, node 22 and bun 1.4.1 alike
(2026-10-18):

| Loop | `maxOps: 200` | `1000` | `10_000` | the default, 1,000,000 |
|---|---|---|---|---|
| `while (true) {}` | 6 ms | 27 to 39 ms | 260 ms | 26 s |
| `while (_event.data.value !== null) {}` | 50 ms | 240 to 250 ms | 2.5 to 2.7 s | about 256 s |

So a check costs 26 to 250 microseconds here, and the default lets one
runaway evaluation stop the process's hosts for minutes. Choose `maxOps`
by the longest stall your other actors can take: a few hundred (5 to 50
ms) for a service that answers requests, 1000 (about 25 to 250 ms) for
background work, and measure your own charts' real work against it,
since an evaluation that needs more checks than `maxOps` fails every
time. `maxOps` does not bound memory: a loop that allocates can take
gigabytes in fewer checks, which `memoryLimit` stops. An evaluation
stopped by `maxOps` gets `error.execution` with `_event.data.reason`
`'fuel'`, one stopped by `memoryLimit` `'memory'`.

## Realms

By default (`realm: 'auto'`) the actors of a chart that declares no
top-level names share one context, each a small scope object, as on the
native datamodel; a chart whose scripts declare top-level names gives
each of its actors a context of its own. The shared context's global object is frozen, so a chart
cannot add globals, but the builtins (`Math`, `Array.prototype`, ...)
are shared by every actor of the host: a chart that changes one changes
it for the others. With `realm: 'isolated'` every actor gets a context of
its own, at the cost of its memory, so no chart sees another's changes.

## What differs from the native datamodel

The same chart runs on both, and what a chart can observe is the same
SCXML. Around the edges:

- **Hibernation stores more.** QuickJS writes its own values into a blob:
  `Date`, `Map`, `Set`, typed arrays and object graphs with cycles come
  back, and a class's instance comes back as a plain object. A function
  in a variable still keeps the actor in memory
  ([Hibernation](hibernation.md)).
- **Values cross by encoding.** Event data and spawn params are converted
  to the engine's values and back, through the same value table
  ([README](../../README.md#values)).
- **Its costs differ.** In the repository's measurements most operations
  cost less on quickjs, and an idle actor takes less memory
  ([Capacity and memory](capacity.md)).

`host.quickjsHeapBytes`, the engine's heap for an operator watching it
against `memoryLimit`, is declared but not built yet: it reads
`undefined` on every host.
